# 六家统 托管逻辑（auto_play）策略说明

本文档说明 Flutter 客户端中的托管逻辑实现，即 `client_dart/lib/core/auto_play/strategy.dart` 中的自动出牌策略，便于与 Python 端、规则实现对齐及后续调整。

---

## 一、总体策略概览

托管逻辑的核心目标是：**在保证出牌合法的前提下，优先出「尽量小」的一手牌**，以实现一种简单、稳定且偏保守的自动出牌行为。

实现步骤（高层）：

1. **按牌面点数分组手牌**：  
   - 将手牌按 `Card.value` 分组，得到 `value -> List<Card>` 的映射。
   - 同时获得所有点数的有序列表 `valuesSorted`（从小到大）。
2. **根据当前轮次信息获取“上家出牌”**：  
   - 从 `FieldInfo` 中读取：
     - 我方座位 `clientId`
     - 上一位出牌人 `lastPlayer`
     - 当前轮到出牌人 `nowPlayer`
     - 本轮各玩家已出牌 `usersPlayedCards`
   - 若上一手是其他玩家出的，则取 `usersPlayedCards[lastPlayer]` 为“上家出牌”；若是自己或场面为空，则视为“无上家出牌”（首出）。
3. **按固定顺序枚举所有候选组合**：  
   - 依次生成以下几类牌型的所有可能组合（详见下一节）：
     1. 单张
     2. 对子
     3. 三张
     4. 顺子
     5. 连对
     6. 连三张
     7. 三带二
     8. 飞机（三顺 + 若干对子）
     9. 炸弹（简单版本）
   - 每一类内部，也会按点数从小到大生成所有组合。
4. **逐个用规则引擎校验合法性**：  
   - 对每个候选组合 `combo`，调用 `validateUserSelectedCards`：
     - 传入：`combo`、完整手牌 `info.clientCards`、以及“上家出牌”。
     - 若规则认为合法（包括牌型合法、能压过上家、牌数量足够等），则立即返回这手牌作为托管结果。
5. **若所有组合都不合法，则选择跳过**：  
   - 若所有候选都无法通过规则验证，托管逻辑返回 `null`，上层调用方会据此选择本轮“跳过”。

> 重点：**托管逻辑本身不直接实现复杂规则判断**，而是依赖 `core/rules/playing_rules.dart` 中的 `validateUserSelectedCards` 来保证规则一致性。

## 二、具体牌型生成策略

设：

- `hand`：当前玩家手牌（`FieldInfo.clientCards`）。
- `byValue`：按点数分组后的映射 `Map<int, List<Card>>`。
- `valuesSorted`：`byValue.keys` 排序后的列表（从小到大）。
- 各生成函数均以同步生成器（`sync*`）形式返回一系列 `List<Card>` 组合。

### 2.1 单张（Singles）

函数：`_generateSingles(byValue, valuesSorted)`

- 对每个点数 `v`，取该点数的任意一张牌 `byValue[v]!.first`。
- 生成顺序：从最小点数到最大点数。
- 用途：在能压过上家的情况下，**优先用最小单张**出牌消耗小牌。

### 2.2 对子（Pairs）

函数：`_generatePairs(byValue, valuesSorted)`

- 条件：`byValue[v]!.length >= 2`。
- 对每个点数 `v`，取前两张牌组成一手对子。
- 顺序同样从小到大。

### 2.3 三张（Triples）

函数：`_generateTriples(byValue, valuesSorted)`

- 条件：`byValue[v]!.length >= 3`。
- 对每个点数 `v`，取前三张牌组成一手三张。
- 仅生成 AAA 形态，不附带其他牌。

### 2.4 顺子（Straights）

函数：`_generateStraights(byValue)`

- 只考虑**不含大小王**、点数在 \[3, 14\]（3 ~ A）之间的顺子。
- 流程：
  1. 收集所有满足 `3 <= v <= 14` 的牌面点数并排序，得到 `cardVals`。
  2. 使用 `_findConsecutiveSegments` 在 `cardVals` 里找出所有“连续片段”（如 \[3,4,5,6,7\]）。
  3. 对每个连续片段 `seg`：
     - 若长度 `< 5`，不构成任何顺子。
     - 对所有可能的长度 `length`（5 至 `seg.length`）：
       - 滑动窗口枚举所有子片段 `sub`，如 \[4,5,6,7,8\]。
       - 对 `sub` 中每个点数，取一张牌 `byValue[v]!.first` 拼成顺子。

> 不使用大小王补顺，也不考虑拆分对/三张来凑顺子，策略偏简单和保守。

### 2.5 连对（Straight Pairs）

函数：`_generateStraightPairs(byValue)`

- 只考虑：
  - 点数在 \[3, 14\] 的牌；
  - 且该点数至少有两张（可组成对子）。
- 步骤与顺子类似：
  1. 找出所有“可成对”的点数并排序。
  2. 找连续片段（至少 2 个点数）。
  3. 对每个长度 ≥ 2 的子片段，依次取每个点数的两张牌拼接，形成 4 张以上的连对，如：`33 44`、`66 77 88` 等。

### 2.6 连三张（Straight Triples）

函数：`_generateStraightTriples(byValue)`

- 条件：某点数至少有三张，且点数连续。
- 步骤与连对相似，只是每个点数取 3 张牌：
  - 至少 2 个连续点数；
  - 对每个子片段长度 ≥ 2 的组合，组成 6 张以上的“连三张”。

### 2.7 三带二（Triple + Pair）

函数：`_generateTriplePairs(byValue, valuesSorted)`

- 生成最简单形式的三带二：`AAA + BB`。
- 流程：
  1. 找出所有可做三张的点数 `triplesVals`（数量 ≥ 3）。
  2. 找出所有可做对子的新点数 `pairsVals`（数量 ≥ 2）。
  3. 对每一个三张点数 `tv`，搭配每一个不同点数的对子 `pv`（`pv != tv`）：
     - 取三张 + 取两张，组成一手 5 张牌。

### 2.8 飞机（Flight：三顺 + 若干对子）

函数：`_generateFlights(byValue, valuesSorted)`

- 只考虑由**连续多个三张** + **等数量的对子**组成的简单“飞机”：
  1. 找出所有点数在 \[3, 14\]，且数量 ≥ 3 的点数组成列表 `tripleVals`，并排序。
  2. 用 `_findConsecutiveSegments` 找出三张的连续片段（至少 2 个连续点数）。
  3. 对每个连续片段 `seg` 和其中的所有子片段：
     - 设长度为 `length`，需要 `length` 个对子做“机翼”。
     - 在所有可成对的点数里，排除三张主体用到的点数，若剩余可成对的点数数量不足 `length`，则无法构成该形态。
     - 否则，取前 `length` 个点数作为“机翼”，按顺序依次：
       - 先拼接所有三张；
       - 再拼接所有对子，得到一手完整飞机牌型。

### 2.9 炸弹（Bombs）

函数：`_generateBombs(byValue, valuesSorted)`

- 条件：某点数的数量 ≥ 4。
- 对每个满足条件的点数 `v`，取前 4 张作为一个“简单炸弹”。
- 当前实现并未区分大小王炸、超长炸、七张以上等特殊炸弹类型，这些细节由规则层（`playing_rules.dart`）判定优先级与比较逻辑。

## 三、出牌决策流程（autoSelectCards）

托管的主入口函数：`List<Card>? autoSelectCards(FieldInfo info)`。

流程描述：

1. 若手牌为空，直接返回 `null`（无牌可出）。
2. 按前述方法构造：
   - `byValue`（按点数分组）
   - `valuesSorted`（点数有序列表）
3. 确定上家出牌：
   - 若 `info.lastPlayer != info.clientId` 且该玩家本轮有出牌，则取其 `usersPlayedCards[lastPlayer]` 为“上家出牌”；
   - 否则视为无上家出牌（首出），传入规则层的 `lastPlayedCards` 为空。
4. 构建牌型生成器列表（按优先级）：

   ```text
   1. 单张
   2. 对子
   3. 三张
   4. 顺子
   5. 连对
   6. 连三张
   7. 三带二
   8. 飞机
   9. 炸弹
   ```

5. 依次遍历每一类生成器和其中的每一个候选组合 `combo`：
   - 调用 `validateUserSelectedCards(combo, fullHand, lastPlayedOrNull)`。
   - 若返回合法，则立即选用该组合作为托管出牌，函数返回这手 `List<Card>`。
6. 若遍历完所有候选组合仍无合法出牌，则返回 `null`，由上层逻辑执行“跳过”。

## 四、策略特性与限制

### 4.1 策略偏保守

- 始终从**点数最小**的组合开始尝试，有利于：
  - 尽量压制上家，同时保留大牌；
  - 对新手或观战托管场景更加“稳健”，不轻易浪费炸弹和高牌。
- 不会主动考虑博弈层面的“留牌结构优化”“为队友留关键牌”等复杂策略。

### 4.2 牌型覆盖与简化

- 支持的主要牌型均与规则层定义一致：单张、对子、三张、顺子、连对、连三张、三带二、飞机、炸弹。
- 但内部生成上做了简化：
  - 顺子、连对、连三张、飞机只使用手牌中现有的、满足最小数量的点数组合，不尝试用大小王“补牌”或复杂拆分。
  - 炸弹目前仅通过“数量 ≥ 4”来生成基础炸弹，大小王炸、超长炸等具体优先级交由规则层控制。

### 4.3 与规则引擎的关系

- 托管策略本身**不判断**：
  - 某组合是否构成合法牌型；
  - 是否压得过上家；
  - 是否满足出牌数量、分数变化等规则。
- 所有这些都由 `playing_rules.dart` 的 `validateUserSelectedCards` 完成。
- 因此，只要规则层保持与 Python 端一致，托管逻辑就能自动继承最新的规则变更。

## 五、后续扩展建议

若需要增强托管智能程度，可在现有策略基础上逐步扩展：

1. **局面感知**：在 `FieldInfo` 基础上引入局面评估（剩余牌结构、队友/对手手牌数等），动态调整优先级。
2. **炸弹管理**：为炸弹添加更精细的触发条件，例如仅在尾盘或关键分数时才主动使用。
3. **分数敏感策略**：结合 `nowScore`、`usersScore`、`headMaster` 等信息，在需要抢分/控分时调整出牌风格。
4. **多方案搜索**：对若干轮之后的收益做简单搜索（如贪心 + 回溯），在多个可行组合中选择更优方案。

当前实现刻意保持了逻辑简单、可读性强，便于与 Python 端托管策略逐步对齐或替换。
